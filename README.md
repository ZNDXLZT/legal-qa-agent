# 法律问答 Agent（飞书 Bot）

一个部署在飞书群内的法律问答机器人，服务企业法务团队的日常咨询。本文说明它如何把一句口语问题变成一份带依据的回答，以及哪些环节容易出错。

仓库里可运行的部分是**离线回放**：读取运行日志中的样例，逐步打印决策过程，不需要联网、不需要模型。

```bash
python3 demo.py        # 列出样例
python3 demo.py 1      # 走完一条的完整链路
```

---

## 1. 问题在哪

法务团队的提问不是起诉状。常见形态是一两句话，没有案由、金额、交易结构：

> 我们准备上线「AI 试妆 + 一键购」。用户上传人脸生成试妆图，可分享、可关水印。

从这句话里，系统需要判断：业务是否涉及人脸信息；是否属于敏感个人信息；平台是处理者还是共同处理者；需要哪些前置合规动作。**这些信息原话里没有一条是明说的。**

另一处约束是准确性。法条与案号不能编，因为用户无法辨识文号真伪——一个不存在的条号读起来比正确答案更专业。

## 2. 六层结构

```
接入层   飞书事件 → 去重 → 取正文 → 建运行记录
判定层   会话状态机：问候 / 元问题 / 追问 / 新任务
理解层   规则打底 → 模型补全 → 规则覆盖，产出结构化简报
规划层   BM25 召回技能候选 → 规则表排序，上限 3 步
执行层   单 Agent 循环调用工具，门控决定是否挂载工具
记录层   每轮落一条执行轨迹，可按消息 ID 回放
```

层间通过字典传递，不共享全局状态。分层的收益是**出错可定位**：回答不准时，能判断是理解偏差、技能选错，还是检索结果没被采用。

## 3. 三个关键决定

### 3.1 简报：结构化优先，纠偏在后

用户的问题先被整理成七个字段——领域、目标、已知事实、缺失信息、假设、立场、检索词。每个字段对应下游一个具体需求，不是「尽量多抽」。

整理过程分三步，对应模型返回的三种坏法：

| 坏法 | 表现 | 处理 |
|---|---|---|
| 不是 JSON | 前面写了「好的，以下是分析」 | 从文本里抠出第一个完整 JSON |
| 是 JSON 但字段不对 | `task_goals` 给了字符串 | 逐字段校验，坏的丢弃 |
| 字段对但内容错 | 把个人信息保护判成民间借贷 | 六条规则覆盖 |

第三条最值得说。模型会把上一轮的事实带进本轮——用户这轮只说「那这个呢」，它却输出「年化 36%」。这个数字在原话里不存在，若不剔除，下游会基于错误前提作答。处理方式是**事实接地**：整体包含判断，或按四字窗口滑动计算命中比例，找不到依据的事实直接丢弃。

### 3.2 技能加载：33 万字节读不完

38 个技能的说明书合计 331,775 字节，全部注入会占满上下文。

改成三层：常驻只有名称与触发条件（9,709 字符），命中后才读该技能正文并删去示例小节（上限 9,000 字符），完整手册留作按需引用——**这一层没有实现**，正文里的链接模型打不开。

单轮注入量从 33 万字节降到 1.2 万字符。

### 3.3 门控：在协议层，不在提示词里

检索接口按次计费。门控规定只有用户明确提出要查法条或案例时，才把工具列表传给模型。

```python
tools = []
if force_mcp:  tools.extend(legal_db.tools)
if force_web:  tools.extend(web.tools)
tools = tools or None          # 不传，模型就没有调用能力
```

**不挂工具，模型从协议上无法调用**，这比在提示词里写「不要调用」可靠。

配套的护栏是零调用拒答：判定需要检索、整轮却没有一次成功调用时，丢弃模型输出，直接返回「检索失败，请核对原文」。

## 5. 两类错误的来源与修复

74 轮日志里能直接找到两类错误。回放工具逐条比对「当时的决策」与「按现有逻辑应做的决策」：

| 错误 | 数量 | 典型语句 |
|---|---|---|
| 元问题误开检索 | 2 | 「调用北大法宝了吗」「你能保证库里没有吗」 |
| 追问漏检 | 9 | 「继续检索这六个」「a 类还有什么类案」 |

第一类白花一次付费调用；第二类该查没查，答案看着正常但没依据。

根因是原实现把所有消息当作新任务。改成四类回合判定后：

```python
if turn is TurnType.FOLLOW_UP:
    explicit = any(k in text for k in ("法宝","检索","查案例","查法条","调用"))
    allow = st.last_mcp or explicit      # 上一轮查过，或本轮明确要求
```

追问的检索权限取「上一轮查过」与「本轮明确要求」的或——**这就是「继续检索这六个」能触发的原因**。

回放结果：误开 2 → 0，漏检 9 → 0，另有 2 处分类边界差异保留。

`demo.py` 的第 3、4 条就是重构前的错误样例，标了 ⚠️，可以直接看到问题形态。

## 6. 评测

三层，从便宜到贵：

| 层 | 规模 | 测什么 | 判据 |
|---|---|---|---|
| 路由 | 55 条 | 领域、技能集合、是否检索 | 与人工期望比对 |
| 检索支撑度 | 10 条 | 材料能否支撑结论 | 相关度 + 支撑度两维 |
| 执行轨迹 | 74 轮 | 决策是否与预期一致 | 新旧逻辑逐条比对 |

55 条里 41 条期望不检索、14 条期望检索。比例刻意如此——门控有误开与漏检两类错，用例全设成「该查」就测不出误开。

其中两组用例是配对的：

```
「快递员拿走包裹算盗窃还是侵占」        → 不检索
「调用法宝查一下……怎么分的判例」      → 检索
```

同一法律问题，区别只在后者明确要求检索。两条一起测，才知道门控是在判意图，还是只看关键词。

## 7. 已知问题

| 问题 | 证据 |
|---|---|
| 意图判断依赖关键词 | 「这个条款还有效吗」召不回效力核查技能 |
| 简报依赖模型 | 每轮多一次调用，结果不可复现 |
| 第三层未实现 | 代码里 `references` 字符串出现 0 次 |
| 评测无人工校验 | 用例期望由单人编写，未做一致性检验 |
| 样本量小 | 7 位使用者、74 轮会话 |

第 4 条是这套评测最实质的缺口：55 条用例的期望都是我自己写的，没有第二个人复核。
